Deploy loop to get a fix from the Mac onto OIST Saion and re-run:

1. Commit + push from the Mac checkout. For gpurec this is `/Users/ssolo/GALE` on branch `cpp-rust-free` (fork `oliver-schick/gpurec`, remote `origin`). SLURM wrappers run the on-disk code and do NOT pull, so unpushed/unpulled fixes silently run stale. See [[feedback-push]].
2. SSH in (non-interactive, key-based, user `gergely-szollosi`; harmless `bind [127.0.0.1]:8888` / `X11 forwarding` warnings print but the session works). NOTE: the bare `ssh saion` alias only resolves ON the OIST network/VPN -- `saion.oist.jp`/`deigo.oist.jp` are internal-only (NXDOMAIN off-network). Off-network, jump through the login node: `ssh -J oist saion` (the `oist` alias = `login.oist.jp`, the public gateway, resolves fine). The config's `saion-ext` is broken (its `oist-ext` jump host is undefined). The saion login node's git is ancient (no `git -C` -- use `cd <dir> && git ...`). Heal the checkout, do NOT `git pull`:
   `git fetch origin && git reset --hard origin/cpp-rust-free`
   Plain `git pull` can conflict/refuse because of the GBs of untracked artifacts (feathers, npz, parquet) in the worktree. `reset --hard` only rewrites tracked files and leaves untracked data intact. Never `git stash -u` -- it hangs for minutes trying to stash multi-GB untracked data. (This SUPERSEDES the earlier `git pull --ff-only origin main` guidance.)
   GOTCHA 2 (hit 2026-06-19, cost MANY failed GPU jobs): every `git reset --hard` updates the **mtime of the C++ sources** (`gpurec/core/cpp/*.cpp/.hpp`), so torch's JIT `cpp_extension` decides the cached ext is stale and **REBUILDS `preprocess_cpp` on the next gpurec import**. That rebuild needs gcc>=9; the only gcc>=9 is the **devtoolset-11 SCL** (`/opt/rh/devtoolset-11/root/usr/bin/g++`, via `module load gcc/11.2.1`; also `gcc/14.2.0`) which is on the LOGIN node but **MISSING on many largegpu compute nodes** -> the rebuild runs `/usr/bin/g++` (8.5) -> "We need GCC 9 or later", OR the absolute devtoolset path -> ninja exit 127 (binary absent on that node). Concurrent jobs racing the same shared `.torch_ext/` make it worse. FIX (the C++ source is normally UNCHANGED by a deploy, only mtime moved): after `git reset --hard`, **`touch .torch_ext/preprocess_cpp/preprocess_cpp.so`** so it is newer than the sources -> torch LOADS the cached .so, NO rebuild, works on any node. The prebuilt `.so` lives in the shared `/work/.../gpurec-cpp/.torch_ext/` so one good build serves all nodes. Only let it rebuild if you actually edited the cpp/hpp (then build once serially on a node that has devtoolset-11, verify, then run the fleet). The Triton kernels (`core/kernels/*.py`) JIT separately (no gcc, no .so) -- Triton 3.2.0 also rejects chained booleans `A and B and C` in kernels (use parens).
   GOTCHA (hit 2026-06-19, cost 2 failed sweep cells): on `gpurec-cpp` the `remote.origin.fetch` refspec was BROKEN, so `refs/remotes/origin/cpp-rust-free` NEVER updated -- `git fetch origin cpp-rust-free` (branch given explicitly) only writes FETCH_HEAD, and `git reset --hard origin/cpp-rust-free` then silently rewinds to a STALE commit (e.g. 1f3efc0), producing a TORN working tree (new driver + old `optimize_theta_wave` -> `unexpected keyword argument 'leaf_E'`) that breaks any SLURM task launching in that window. FIX once: `git config remote.origin.fetch "+refs/heads/*:refs/remotes/origin/*"`. Then ALWAYS deploy with plain `git fetch origin` (NO branch arg) so the remote-tracking ref advances, or use `git reset --hard FETCH_HEAD` right after the fetch. Verify HEAD after reset: `git log --oneline -1` must show the commit you just pushed. Resetting the SHARED checkout while array tasks are pending risks torn-state failures -- re-`sbatch --array=<failed idx>` to heal individual cells (the sweep skip-logic `[ -s "$ratefile" ]` re-runs only missing outputs).
3. Relaunch via the launcher (which `sbatch`es). Launchers should be resume-safe: skip splits that already have their checkpoint/`done.flag`, and per-stage `progress.json` resume skips completed stages. No SLURM (sbatch/squeue/scancel) on the Mac.
4. Before relaunching, check `squeue --me` -- a fresh launch re-queues not-done splits and would collide with any in-flight job on the same outdir. Cancel stale failing chains first.
